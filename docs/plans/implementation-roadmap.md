# 구현 순서와 검증 기준

상태: 전체 목표 구현 계획. 실행일·자동 순환의 현재 구현은 [현행 구조](../../server/docs/architecture/automatic-duties.md)를 우선한다. 아래 초기 비교 표와 수동 확정/checkpoint 단계는 최초 기준이며 현재 신규 생성 UX의 필수 단계가 아니다.

## 1. 현재와 목표의 차이

| 영역      | 현재 구현                                     | 목표                                         |
| --------- | --------------------------------------------- | -------------------------------------------- |
| 업무 발생 | 실행 일정·교대 분리, 자동 순환                | 발생 규칙과 교대 규칙 분리                   |
| 회사 휴일 | 휴일 등록·실행 없음·교대 유지                 | 근무일 캘린더, 발생 없음/주간 순환 유지      |
| 규칙 변경 | 기본정보·참가자·순서·인원 버전 편집 및 검토   | 적용일이 있는 불변 버전·변경 이력            |
| 참여자    | 현재 직원 정보 참조                           | 버전별 명단·사번 순서 snapshot               |
| 직원 상태 | active boolean                                | 날짜별 상태 구간                             |
| 확정      | 명시적 배정 범위 생성·연장, 조회 시 저장 금지 | 첫 미확정부터 연속 저장·checkpoint           |
| 미리보기  | periods.toString hash                         | 서버 임시 snapshot·만료·입력 revision        |
| 중복      | 동일 업무 UNIQUE·동일일 교차 업무 경고        | 전사 기본 경고, 한쪽 FORBID면 차단           |
| 대타      | 기간 employee 갱신                            | 미래 발생 건만 갱신, 과거 담당 snapshot 보존 |
| 제외      | 추가만 가능                                   | 수정·취소와 확정 영향 검사                   |
| API       | /api, 숫자 ID, {message} 오류                 | /api 유지, 문자열 ID·구조화된 오류·멱등성    |
| DB        | V1~V7의 19개 테이블                           | 버전·발생 건·checkpoint·감사 관계 정규화     |
| 인증/알림 | 미구현                                        | 로그인 후 공개, 메일·Pepper는 별도 후속 단계 |

현재 파일:
[現在のDutyモデル](../../server/src/main/java/com/dutymanager/model/duty/Duty.java),
[AssignmentEngine](../../server/src/main/java/com/dutymanager/engine/rotation/AssignmentEngine.java),
[DutyService](../../server/src/main/java/com/dutymanager/service/duty/DutyService.java),
[V1 schema](../../server/src/main/resources/db/migration/V1__initial_schema.sql).

현재 V1 SQL과 기존 테스트를 목표 설계에 맞춘다고 먼저 삭제하거나 덮어쓰지 않는다.

## 2. 권장 구현 순서

### A. 자료형·순수 계산기

- 목표 DTO/domain 및 구조화된 오류 정의.
- DateRange/회사 근무일/발생 규칙과 RotationRule 분리.
- 월간 제N요일·말일·휴일·담당 기간 경계 단위 검증.
- 고정 순서/랜덤/복수 인원과 checkpoint의 재현성 검증.

완료: API·DB 없이 명확한 입력→출력으로 공통 정책의 일정 예시를 계산한다.

### B. 스키마 확장·이행 준비

- 실제 DB 상태와 데이터 유무 확인, 이행 보고서 생성.
- 새 테이블/nullable 컬럼의 Flyway expand.
- 기존 ID·확정 담당·이력 보존 backfill.
- 사번 충돌·발생 일정 미지정·비연속 확정의 검토 항목 분리.
- MySQL 8.4에서 제약·잠금·시간대 round-trip 검증.

완료: V1 데이터와 신규 모델 대조, 되돌릴 방법, 쓰기 중단/전환 방식이 준비된다.

### C. 운영 API

- 회사 캘린더·직원 상태·업무 초안/버전 CRUD.
- preview/confirm, 공통 잠금, expected version, 멱등 키.
- 대타·제외 수정/취소·발생 건 이동/취소·이력.
- 기존 API를 새 application service의 단일 쓰기 경로로 전환.

완료: API에서 승인한 결과와 DB 전체 저장 결과가 일치하고 충돌 시 rollback된다.

### D. UI 연결

- 기존 Axios → API → Repository → Hook → UI 구조 유지.
- 목표 DTO/mapper, 구조화된 오류, 문자열 ID의 서버·클라이언트 동시 전환.
- 당번 기본정보·발생 일정·교대·참여자·적용일·검토 화면.
- 전체 실제 확정 범위와 휴일/중복/0건 경고.
- 캘린더·대타·제외·버전 이력 화면.

완료: 화면에서 규칙을 입력하고 검토·확정·변경하는 흐름을 일본어로 수행한다.
UI가 배정 알고리즘을 자체 구현하지 않는다.

### E. 실무 시나리오 검증

회사의 실제 근무일, 직원 명단, 쓰레기 배출 요일, 정례회 일자를 입력한다.
아래 예시의 직원명·시간을 회사 실제 정보라고 가정하지 않는다.

### F. 후속

로그인/권한 → 사내 테스트 배포 → 메일 → Pepper.
일반 직원에게 공개하기 전 서버 권한 검사와 audit actor 연결을 완료한다.

## 3. 인수 시나리오

| ID  | 조건/행동                               | 기대 결과                                                    |
| --- | --------------------------------------- | ------------------------------------------------------------ |
| P01 | 주간 A, 화·수 휴무                      | 월·목·금 A, 다음 월 B. 보충/교체 지연 없음                   |
| P02 | 한 주 전체 휴무                         | 발생 0건 경고, 달력 기준 주간 교대 유지                      |
| P03 | 금요일 배출 업무의 금요일 휴무          | 기본 발생 없음. 월요일로 자동 이월하지 않음                  |
| P04 | 매월 다섯째 금요일이 없는 달            | 해당 발생 없음. 다음 달 규칙 날짜는 원래 기준 유지           |
| P05 | 1/31 기준 월간 교대                     | 2월 말일, 다음은 3/31                                        |
| P06 | 주간 중 하루 제외                       | 그 주 전체에서 후보 제외, 이후 자동 우선 보상 없음           |
| P07 | 여러 번 미리보기/새로고침               | 후보와 checkpoint 불변, 순환 미소비                          |
| P08 | 랜덤 1명·제외 없음                      | 전원 한 번 후 다음 라운드, 재조회 결과 동일                  |
| P09 | 랜덤 여러 명·라운드 경계                | 같은 기간 중복 없음, 보류 후보 유실 없음                     |
| P10 | 서로 다른 업무 ALLOW                    | 겹침 경고를 보고 확인 후 저장 가능                           |
| P11 | 두 업무 중 한쪽 FORBID                  | 금지 중복 확정·대타 차단                                     |
| P12 | 다른 관리자가 동시에 FORBID 배정        | 한 요청 성공, 나머지는 최신 재검증에서 충돌                  |
| P13 | preview 뒤 제외/직원/캘린더 변경        | 409, 저장 없음, 재미리보기 필요                              |
| P14 | 인원이 부족한 구간 포함 확정            | 전체 rollback, 부분 저장 없음                                |
| P15 | 확정 응답 유실 후 같은 키 재시도        | 같은 응답, 중복 배정/순환 소비 없음                          |
| P16 | 같은 키로 다른 본문                     | 409, 원래 성공 결과 보존                                     |
| P17 | 미래 배정이 있는 구간부터 규칙 변경     | 과거·진행 중·수동 보호를 유지하고 영향 미리보기 승인 후 적용 |
| P18 | 미래 대기 버전 수정                     | 취소 이력 후 새 버전, 버전 번호 재사용 없음                  |
| P19 | 사번/직원명 변경                        | 직원 ID 유지, 과거 확정 snapshot·순환 정렬 보존              |
| P20 | 확정 담당에 겹치는 비활성/제외          | 대타 선행 안내, 자동 삭제 없음                               |
| P21 | 진행 중 주간 기간 대타                  | 남은 발생 건만 새 담당, 지난 발생 건과 다음 순서 유지        |
| P22 | 개별 정례회를 다음 기간으로 이동        | 담당 영향 확인, 대상 기간 확정·적격성 검사                   |
| P23 | 확정된 미래 회의일을 회사 휴일로 변경   | 영향 검토 후 발생 건 취소, 기간 담당/checkpoint 유지         |
| P24 | 수동 취소된 회의의 휴일 해제            | 수동 취소는 그대로. 자동 부활 없음                           |
| P25 | 조회 기간보다 앞선 미확정 구간 존재     | 전체 연속 확정 대상 표시, 숨은 행 저장 없음                  |
| P26 | 구형 숫자 ID/period_end 이행            | ID 보존, inclusive→exclusive 하루 경계 정확                  |
| P27 | Tokyo 업무 날짜·UTC 기록 시각 저장/조회 | 브라우저/DB session 차이로 업무 날짜 이동 없음               |
| P28 | MEMBER의 관리 API 직접 호출             | UI 노출 여부와 무관하게 서버 403                             |

현재 코드가 위 시나리오를 모두 통과한다고 주장하지 않는다.
단위 검증은 순수 계산기, DB 무결성·동시성은 실제 MySQL, UI 흐름은 사용자 이벤트 기반으로 검증한다.

## 4. 이후 확정할 운영 정보

- 실제 직원 명단과 사번 표기.
- 실제 쓰레기 배출 요일/휴일 수행 여부.
- 정례회의 실제 반복 규칙 또는 개별 일자.
- 퇴근 시각과 금요일이 휴무일일 때의 알림 정책.
- 인증 수단과 관리자 지정.
- 회사 데이터 보존 기간과 배포·복구 운영값.

사용자에게 이미 합의받은 휴일/중복 기본 정책을 다시 미결 사항으로 돌리지 않는다.

## 규칙 편집 후속 기준（2026-10-27）

[참가자·규칙 변경 정책](../policies/rule-change-policy.md)의 합의된 정책을 우선한다. 미래 자동 배정의 명시적 재검토·변경과 다음 차례 이어가기를 지원한다. 조회로 저장된 배정과 수동 보호를 구분하고, 신규 참가자의 방식별 편입과 랜덤 잔여 큐 보존을 반영하고, 수동 보호 충돌을 검토 화면에서 함께 해결하도록 설계하고, 배정 방식 전환·퇴사·복귀 등 남은 미합의 항목을 결정한 뒤 API·DB 상세를 확정한다. 이 단계는 문서 정책 합의이며 런타임 구현이 아니다.

[운영 기간·담당 배정 범위 정책](../policies/allocation-window-policy.md)을 현행 생성·연장 기준으로 따른다. 위 목표 단계는 전체 구현이 끝났다는 의미가 아니다.
